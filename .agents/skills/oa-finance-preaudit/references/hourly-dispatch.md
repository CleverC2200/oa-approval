# 小时检查与连续处理

本文件仅供定时任务及其接续对话的主 Agent 读取。审核与排空使用[批次执行规则](batch-execution.md)，业务审核使用 [Skill](../SKILL.md) 的流程路由。授权统一遵循 [SECURITY.md](../../../../SECURITY.md)。

## 启动与互斥

每小时检查用于空闲时发现待办。有积压时保存接续预留，由下一次实际权限及项目环境符合要求的小时对话消费。每次调度对话只处理一个批次。自动任务保持用户设定的启停状态；暂停后不创建新接续对话。

1. 从 `/Users/synear/Documents/OA` 读取当前 AGENTS.md。小时任务及接续固定使用 `/Users/synear/Documents/OA/runtime/hourly-preaudit`，保留同一 SQLite 账本与材料。首次使用共享锁版本前确认旧版本 owner 已结束，正在审批的 checkout 保持原样，空闲后再同步主线。
2. 用公开 `approvals --root <固定目录> status --view batch` 检查已有轮次、`alerts` 及 owner，按下文处理异常。健康且身份匹配的 owner 可达时跳过本轮；忙碌或探测不明先复查，不当作已退出。失联的 running/blocked 或未知提交先报告核对。最新轮次 closed、handoff 为 ready 且 owner 明确不可达时，核对任务仍 ACTIVE、没有停止指令或未知提交，再用该精确 run_id 执行 `start --continue-from <run_id> --limit 0`。不得另开初始轮绕过预留。
3. 空闲后 fetch `origin/main`，确认分支为 main、工作区干净且 HEAD 与 `origin/main` 一致。失败即停止，不自动切换、重置或拉取合入。
4. 初始轮使用 `start --batch-size 40 --limit 0`，显式限定当前授权的流程。非 demo 的审批入口先取得项目共享 `runtime/approval.lock`，再取得本轮目录锁；任一 runtime 有 owner 时，第二个启动返回 `already_running`，尚未读取 OA 或建立队列。收到该状态直接跳过，不等待或换目录绕过。

### 失联轮次核对

存在 `unknown` 或 `submitting` 时，先用 `postcheck --task-id <精确任务ID>` 核对。owner 已关闭或失联时，同一入口从干净且同步的 main 取得共享互斥后只读回查 OA，并保存回执；不创建新轮、不重发。回查仍为未知或读取失败时保持停止；确认成功后再核对轮次关闭状态和当前待办。

仅当当前用户明确确认某次提交未写入时，可在同一 `postcheck` 增加 `--confirm-not-written YES --expected-submission-id <已核对的提交尝试ID> --confirmation-note <本次人工确认原文及依据>`。入口须再次确认仍为同一投递待办、没有该次已办证据，才将该尝试记录为用户确认未写入的 `failed`，保留确认内容、原回执及意见。投递身份变化、已办冲突或读取失败时不解除未知保护；已核实成功时仍按成功回执处理。该入口不提交 OA，后续仅按本次授权重新采集和完整审核；海外不支持此确认分支。待办仍在、超时、未找到已办或旧授权都不能替代本次人工确认。

已关闭最新轮次遗留 `reviewed` 且确定属于写前技术失败时，须有当前用户对本次问题的修复授权，再通过 `fail --task-id <ID> --closed-run-id <精确轮次ID> --expected-review-id <公开show取得的最新意见ID> --reason <已核原因>` 登记本地失败。入口持有共享互斥，核对 owner 已退出、无活动采集或未核实提交、目标为同轮待提交意见且从未开始提交；保留意见和材料，不访问 OA。该入口不能处理原仅预览、未知或已开始提交的投递。后续重试仍须本次授权精确指定申请，并重新采集和完整审核；小时任务不自动执行此修复。

失联轮次保持停止，先核对原对话终态、进程及公开批次回执。当前用户明确授权处理失联轮次后，可用 `finish --run-id <精确旧轮ID> --orphaned` 显式关闭。该入口取得共享锁及批次锁，核对最新轮身份、socket 不可连接、没有未结束采集和未核实提交后，仅关闭本地轮次，保留任务状态、意见、材料及回执；不恢复旧审核或生成接续。若仅因遗留 `preparing` 返回 `collection_unresolved`，先核对原对话已终止、owner 及采集进程均已退出，并取得当前用户对该精确轮次的处理授权；满足后在同一 `finish --orphaned` 增加 `--collection-stopped-note <本次授权原文及进程核对依据>`。该确认随关闭事实持久化，任务、材料和意见保持原样，不证明业务审核完成，也不允许跳过未知提交保护。无法确认进程退出时保留现场；其他拒绝按具体原因处理，未知提交仍只读回查。关闭后确认旧轮 closed，再按初始启动规则重新拉取待办和完整审核。进程收到 SIGTERM 或 SIGHUP 时按正常退出收尾，等待当前采集落盘并释放锁；强制终止仍须核对失联轮次。

## 持续补位与对话轮换

- 每个主对话最多领取 40 单，批次内保持最多 3 单在途，一单结束后及时补位。审核 Agent 每代最多 5 单及换类型轮换沿用批次执行规则。完整业务核对要求保持不变。
- 有积压就持续处理，取消按运行时长停止补位。主对话可见上下文达到窗口 60% 或已经影响读取质量时，提前停止领取并排空；平台未提供可靠占用时使用 40 单边界，不估造 token 数。
- 主 Agent 仅保留状态、身份和文件引用。CLI 原始 JSON、完整材料、意见和逐页结果保存在 runtime，审核 Agent 从文件完整读取。
- 初始待办不足 40 单时处理实际数量。技术失败和预览也占领取数；连续链内已处理的任务身份保存在账本，后续轮不重复预览或重试失败单。OA 再次投递的新任务身份仍可进入队列。

## 保存接续并结束

先按[批次关闭分支](batch-execution.md#正常完成与关闭轮次)逐单验收并选择关闭命令。计划 ACTIVE、没有停止指令或未知提交时，执行一次 `finish --run-id <本轮ID> --require-drained --handoff`，保存关闭回执，等待原 owner 工具会话退出，再核对 `run.status=closed`、`owner.reachable=false` 及本批收尾验收。

- `handoff.status=ready`：报告剩余数量并结束，等待下一次小时触发消费。当前对话不循环启动下一批，不创建或 fork 聊天，不创建工作树。
- `done`：当前队列耗尽，等待下次小时检查。
- `blocked`：保留并报告具体原因，停止接续。

暂停或用户停止后不消费预留、不领取新单。未知提交只读回查。接续继续保留原流程、授权和每轮上限，重新采集、完整审核，不复用旧未完成意见。

接续预留在关闭回执前写入 SQLite。普通 start 在预留待消费时返回 `continuation_pending`，不刷新 OA。`--continue-from` 只允许消费最新且 ready 的前轮一次；已经消费、错误身份或变更流程范围均在刷新 OA 前拒绝。下一轮排除本连续链已完成、已预览或明确失败的同一次投递，保留失败材料和回执；旧轮和原对话不再接单。

## 采集停滞与历史失败

`status` 的 owner 信息同时报告 `phase` 和采集耗时、总时限、当前阶段及剩余时限。owner 可达只证明服务响应；观察到采集长时间无进展时报告采集信息，保持互斥及提交保护，不将其视为业务审核完成。采集总时限及浏览器读取、下载、清理的阶段时限由 owner 在浏览器进程外监视；超过任一适用时限后受控结束，仅把仍在 preparing 的单据登记为技术失败，保留材料和其他任务事实。停止与关闭仍等待这次有界收尾。

历史失败投递在新的初始轮也默认排除。只有本次用户明确授权重试指定投递时，初始启动才可增加 `--retry-failed YES --request-id <精确单号>`；不能用于接续，也不授予真实提交或海外权限。新的投递身份仍按当前待办进入队列。小时任务不自动添加该参数。

## 结束与反馈

无待办也按批次规则验收 owner 退出。每轮报告只含领取数、已验证提交/预览/技术失败数、未领取数、接续状态、耗时及证据路径。区分队列耗尽、对话轮换、已有运行跳过和异常阻断。

`status --view batch` 的 `alerts` 表示当前事实，不以命令退出码或聊天结束状态代替验收：

| 告警 | 接管方式 |
| --- | --- |
| `owner_unresponsive` | 执行者忙碌或探测结果不明。间隔 30 秒复查同一轮，核对原 owner 进程和工具会话，不判为失联、未知提交或已退出 |
| `owner_unreachable` / `owner_mismatch` | 间隔 30 秒复查同一轮并核对原对话、进程及身份；确认异常后报告并保留现场，不自动恢复或关闭旧轮 |
| `submission_unresolved` / `submission_unverified` | 停止补位和其他写入，仅用公开 `postcheck` 核对；正常同步执行的提交只阻止提前收尾，不单独误报未知提交 |
| `run_blocked` / `run_closed_with_inflight` | 报告停止原因或未完成范围，不把 closed 当作完成，不恢复旧审核 |
| `technical_failures` | 报告数量和具体错误的证据路径，其余任务按原授权继续 |
| `continuation_pending` | 保存接续事实，按既定的下一次小时触发规则消费，不创建额外对话 |

首次发现阻断或已核实的审核停滞，在当前对话说明原因、实际轮次或 Agent、最后事件及需要的处理；同轮同原因只报告一次，新事实再更新。通知偏好沿用自动任务的既有配置，不新增独立收件箱投递、后台监控或飞书消息。

意见、数据库和回执保持私有；自动任务记忆不累积业务材料、历史单号或旧队列，只保留原因代码及证据引用。
