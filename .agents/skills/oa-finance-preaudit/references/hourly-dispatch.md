# 小时检查与连续处理

本文件仅供定时任务及其接续对话的主 Agent 读取。审核与排空使用[批次执行规则](batch-execution.md)，业务审核使用 [Skill](../SKILL.md) 的流程路由。授权统一遵循 [SECURITY.md](../../../../SECURITY.md)。

## 启动与互斥

每小时检查用于空闲时发现待办。有积压时保存接续预留，由下一次实际权限及项目环境符合要求的小时对话消费。每次调度对话只处理一个批次。自动任务保持用户设定的启停状态；暂停后不创建新接续对话。

发布后启用本分支时，小时任务提示保留业务授权、排除项和环境，引用本文件的启动、异常收尾与回报规则。提示中的启动条件与本文件同步后，在下一次正常小时触发验收，正在审批时先等待原轮收尾。

1. 从 `/Users/synear/Documents/OA` 读取当前 AGENTS.md。小时任务及接续固定使用 `/Users/synear/Documents/OA/runtime/hourly-preaudit`，保留同一 SQLite 账本与材料。首次使用共享锁版本前确认旧版本 owner 已结束，正在审批的 checkout 保持原样，空闲后再同步主线。
2. 核计划仍 ACTIVE，检查用户停机指令。用公开 `status --view batch` 读取最新轮的 `hourly_dispatch`、owner、`runtime_unresolved`、采集/Writer 阶段和 `review_progress`。按[进度与失联核对](#进度与失联核对)处理 `inspect_owner`、`confirm_stopped` 或 `postcheck`。`stopped`、`blocked` 保留原因并结束本次检查。
3. 空闲后 fetch `origin/main`，确认分支为 main、工作区干净且 HEAD 与 `origin/main` 一致。失败即停止，不自动切换、重置或拉取合入。
4. 所有小时启动使用 `start --hourly`。`continue` 使用 `--continue-from <精确前轮ID> --limit 0`，沿用原选择。首次运行或 `start` 使用 `--batch-size 40 --limit 0` 和当前授权流程及排除项。按下文带上适用的失败恢复项。入口持有共享锁和本轮锁，并在获取待办前重查 socket、Writer 锁、停机、写入回执和接续预留。返回 `already_running` 时按正在运行处理，不换目录绕过。下一轮仍只处理一个批次。

### 差旅对账名单

在 OA 私有认证文件同目录配置 `travel-reconciliation-sheet.json`，填写 `spreadsheet_token`、`sheet_id` 和具备该表读取权限的 `identity`（`user` 或 `bot`）。配置和名单放在私有目录。

每次实际启动小时轮次（含接续），入口通过 `lark-cli sheets +table-get` 重新读取子表，并把结果保存到本轮独立文件。`start` 和 `status --view batch` 的 `travel_reconciliation` 显示读取状态、时间、含工号的行数及快照路径。读取失败保留失败原因。名单快照目前只供核对。

### 进度与失联核对

状态不明时相隔 30 秒核对同一轮，检查原对话和工具会话、对应 PID 和启动时间、采集/识别/审核进度、阶段时限和 Writer 回执。可达、待办数量和运行时长各自都不足以判定卡死。正常在途或服务端明确退避时保留原轮继续。个别审核异常按[批次停滞规则](batch-execution.md)核实终态，隔离失败单并保留其余正常审批。缺少可核实的进程或阶段证据时报告具体缺口。

已有一次性授权的本小时任务，可以处置该固定 runtime 的确认失联或卡死。核实整轮卡死且没有正常在途单据时，先保存最后有效事件和原轮身份。执行进程仍可达时，可用绑定精确 run_id 的 `finish --stop-file` 记录 `execution_incomplete` 并尝试受控收尾。执行进程无响应时，用原生工具会话核对并停止精确原进程，优先受控终止。确认过程继续检查采集、Writer 和未核实提交。只有核实身份、原进程仍卡死、已无活动子进程且无未核实写入时，才可强制终止该精确进程。始终确认原审批和外部工具会话均已退出，其他仍在运行或身份不明的进程保留现场。未领取队列不阻止确认卡死后的收尾。

确认退出、无未核实写入、没有停机且无 ready 预留时，在本次小时触发以正常初始范围运行 `start --hourly --stopped-run-file <本 runtime 内绝对路径>`。JSON 提供 `run_id`、`basis` 和 `evidence`。`basis` 为 `owner_lost`、`execution_stalled` 或 `orphan_close_receipt`，`evidence` 记录核对时间、原对话终态、工具与进程退出证据引用。旧版缺少关闭来源时，已有授权失联关闭可用同一精确轮次的成功回执，并重新核对当前状态。入口持锁记录旧轮关闭事实后才刷新 OA，返回 `recovered_run` 和新轮启动回执。中断在这两步之间时，下次凭已持久化的 `closure` 启动。先核清导致接续阻断的写入保护，再按同一退出证据处理已失效预留。接续因本轮没有进展而阻断时，保留原因并停止。旧轮仍未确认提交的材料按提交保护规则留存。历史关闭状态使用 `closed_batch` 和 `execution` 验收。没有小时恢复授权时走下文人工失联关闭。

存在 `unknown` 或失联 Writer 遗留的 `submitting` 时，先用 `postcheck --task-id <精确任务ID>` 核对。owner 已关闭或失联时，同一入口从干净且同步的 main 取得共享互斥后只读回查 OA，并保存回执；不创建新轮、不重发。回查仍为未知或读取失败时保持停止；确认成功后再核对轮次关闭状态和当前待办。`runtime_unresolved` 同时列出其他轮次仍未知或未结束的写入；即使本轮无任务，也继续阻止正常关闭和成功归档。回查不自动解除 blocked 轮次。

人工确认仅消费当前用户对精确提交尝试的确认。普通提交须明确确认未写入；海外节点未提交的适用条件与字段回填事实按[海外规则](../../oa-overseas-invoice/SKILL.md#人工确认节点未提交)执行。在同一 `postcheck` 增加 `--confirm-not-written YES --expected-submission-id <已核对的提交尝试ID> --confirmation-note <本次人工确认原文及依据>`，核对通过后将该尝试记录为已确认失败，保留确认内容、原回执及意见，不计审批成功。投递身份变化、已办冲突或读取失败时保留未知保护；已核实成功时仍按成功回执处理。该入口不提交 OA，后续仅按本次授权重新采集和完整审核。待办仍在、超时、未找到已办或旧授权都不能替代本次人工确认。

已关闭最新轮次遗留 `reviewed` 且确定属于写前技术失败时，须有当前用户对本次问题的修复授权，再通过 `fail --task-id <ID> --closed-run-id <精确轮次ID> --expected-review-id <公开show取得的最新意见ID> --reason <已核原因>` 登记本地失败。入口持有共享互斥，核对 owner 已退出、无活动采集或未核实提交、目标为同轮待提交意见且从未开始提交；保留意见和材料，不访问 OA。该入口不能处理原仅预览、未知或已开始提交的投递。后续重试仍须本次授权精确指定申请，并重新采集和完整审核；小时任务不自动执行此修复。

人工失联关闭先核对原对话终态、进程及公开批次回执。当前用户明确授权处理精确失联轮次后，可用 `finish --run-id <精确旧轮ID> --orphaned` 显式关闭。该入口取得共享锁及批次锁，核对最新轮身份、socket 不可连接、没有未结束采集和未核实提交后，仅关闭本地轮次，保留任务状态、意见、材料及回执；不恢复旧审核或生成接续。若仅因遗留 `preparing` 返回 `collection_unresolved`，先核对原对话已终止、owner 及采集进程均已退出，并取得当前用户对该精确轮次的处理授权；满足后在同一 `finish --orphaned` 增加 `--collection-stopped-note <本次授权原文及进程核对依据>`。该确认随关闭事实持久化，任务、材料和意见保持原样，不证明业务审核完成，也不允许跳过未知提交保护。无法确认进程退出时保留现场；其他拒绝按具体原因处理，未知提交仍只读回查。关闭后确认旧轮 closed，再按初始启动规则重新拉取待办和完整审核。进程收到 SIGTERM 或 SIGHUP 时按正常退出收尾，等待当前采集与 Writer 落盘并释放锁；强制终止仍须核对失联轮次。

## 持续补位与对话轮换

商旅账号或公司配置缺失按[商旅 SSO 受限交接](travel-sso-handoff.md)执行。公开采集入口自动绑定已保存的通用授权；已形成受限材料且适用审核完成时按业务待核提交并继续 FIFO，不先登记技术失败再尝试恢复。

- 每个主对话最多领取 40 单，准备、审核及唯一 Writer 按[批次容量和补位规则](batch-execution.md#冻结批次与领取)并行推进，交付保存成功后及时补审核空位。审核 Agent 按批次执行规则按需复用或轮换。完整业务核对要求保持不变。
- 有积压就持续处理，取消按运行时长停止补位。停止条件按[提交前审核结果](review-assessment.md)区分业务待核和实际读取失败；业务待核单按适用规则处理后继续补位。平台未提供可靠上下文占用、也没有实际读取失败或截断时，使用40单或真实队列边界，不估造 token 数。
- 单据采集经两次同源读取确认开票名称基准不可用时，回传 `waiting/source_unavailable` 并保留证据。按 `status --view batch` 的 `source_pause.waiting_task_ids` 和 `next_candidate` 继续补位。候选仅来自原冻结批次，暂缓单保留原接收顺序和待办状态。
- 只剩来源暂缓单时，照常推进已领取单，并等到回执中的 `recheck_at` 复查一次。到时先核对停机、未知提交和当前候选，再重采原顺序最早的可领取单。来源恢复后在本轮继续补位。复查仍暂缓且已无其他可领取单时，排空已领单并保存接续，由下一小时重新取证。
- 单据采集、解析或识别失败时保留本单证据并登记技术失败。已核故障局限本单、owner 及其他任务正常时继续补位；缺少明确影响范围的共享读取服务故障、主对话正文分页连续性无法恢复或平台明确报告上下文不足时，保存实际证据后停止新领并排空。上下文百分比仅作诊断，不作为固定提前停止阈值。`unknown`、失联 Writer 遗留的 `submitting` 及身份或材料归属冲突仍按批次保护停止；正常活动 Writer 不阻止采集或审核补位。
- 主 Agent 仅保留状态、身份和文件引用。CLI 原始 JSON、完整材料、意见和逐页结果保存在 runtime，审核 Agent 从文件完整读取。
- 初始待办不足 40 单时处理实际数量。技术失败和预览也占领取数；连续链内已处理的任务身份保存在账本，后续轮不重复预览或重试失败单。OA 再次投递的新任务身份仍可进入队列。

## 保存接续并结束

先按[批次关闭分支](batch-execution.md#正常完成与关闭轮次)逐单验收并选择关闭命令。计划 ACTIVE、没有停止指令或未知提交时，执行一次 `finish --run-id <本轮ID> --require-drained --handoff`，保存关闭回执，等待原 owner 工具会话退出，再核对 `run.status=closed`、`owner.reachable=false` 及本批收尾验收。

本批还有未领取单而提前结束时，按下表增加 `--stop-file <私有JSON绝对路径>`。本批所有余单都在 `source_pause.waiting_task_ids` 且本轮复查仍不可用时，直接用上方命令保存接续，入口使用已有的来源诊断。

| `kind` | 必需事实 |
| --- | --- |
| `context_limit` | `reason` 和 `evidence_file` 指向平台明确报告上下文不足的证据；平台提供百分比时可附 `context_used_percent`，不自估，也不以固定百分比代替实际缺口 |
| `material_read_failure` | `reason`、`task_id` 指向本轮已登记失败且有具体错误的任务；不得指向仅有业务待核的已提交单 |
| `execution_incomplete` | `reason`、`evidence_file` 保存可定位的截断或执行未完成证据；按异常汇报 |
| `authorized_handoff` | `reason`、`evidence_file` 保存已完成阶段目标和交接授权的证据，随 `--require-drained --handoff` 提交。回报已验证和待接续数量；本轮实际失败继续按失败事实汇报 |
| `user_stop` | `reason` 保留本次停止指令；不消费或新建接续 |

关闭快照保留本轮验证提交、失败、预览和未领取数。全部余单因来源故障暂缓时，入口保存 `source_unavailable` 和诊断引用。接续预留已保存时，报告来源暂缓和待接续数。有其他失败时，首行照实报告失败，正文另列暂缓和待接续。其他无停止依据的提前关闭记为 `unexplained`。EOF、信号和失联关闭同样保留实际未完成范围。停止证据由入口复制到本轮独立证据目录，源文件后续变化不改写关闭事实。

- `handoff.status=ready`：报告剩余数量并结束，等待下一次小时触发消费。当前对话不循环启动下一批，不创建或 fork 聊天，不创建工作树。
- `done`：当前队列耗尽，等待下次小时检查。
- `blocked`：保留并报告具体原因，停止接续。

暂停或用户停止后不消费预留、不领取新单。未知提交只读回查。接续继续保留原流程、授权和每批领取上限，重新采集、完整审核，不复用旧未完成意见。

接续预留在关闭回执前写入 SQLite。普通 start 在预留待消费时返回 `continuation_pending`，不刷新 OA。`--continue-from` 只允许消费最新且 ready 的前轮一次；已经消费、错误身份或变更流程范围均在刷新 OA 前拒绝。下一轮排除本连续链已完成及已预览的同一次投递；失败仅可按下节的明确恢复授权重审一次，之后继续排除并保留证据。旧轮和原对话不再接单。

## 采集停滞与历史失败

采集失败先用公开 `show --task-id <ID>` 核对 `task.error` 与 `collection_failure`，再读取回执的 `diagnostics_file` 及适用的 `read_results_file`。`collection_deadline` 的 `stage` 区分读取与浏览器清理；清理前保存的读取状态和观察只用于定位故障，不替代完整冻结材料或提交验收。汇报分别说明依赖可达、完整采集和提交验证的实际证据；错误码或依赖恢复本身不能证明后两项完成。

`status` 的 owner 信息同时报告 `phase`、`writer` 的任务/操作/PID/耗时，以及采集耗时、总时限、当前阶段及剩余时限。owner 可达只证明服务响应；观察到采集长时间无进展时报告采集信息，保持互斥及提交保护，不将其视为业务审核完成。采集总时限及浏览器读取、下载、清理的阶段时限由 owner 在浏览器进程外监视；超过任一适用时限后受控结束，仅把仍在 preparing 的单据登记为技术失败，保留材料和其他任务事实。停止与关闭仍等待这次有界收尾。

历史失败默认排除。当前用户已授权自动任务恢复既定范围内技术失败时，从公开 `status --view batch` 的 `recovery_candidates` 取得候选；该清单只包含当前范围内、已登记失败且从未开始提交、尚未做过恢复尝试的已知投递。恢复后再次失败不再列入后续小时候选，保留原因等待实际修复及新的精确授权。按清单逐个传入 `--recover-request-id <申请ID>`，无需对已覆盖的授权重复询问。入口仍重新拉取真实待办，已离开待办的旧身份不进入重审。出现过提交尝试的失败、未知提交和原仅预览不走自动恢复，按对应分支核实。

人工明确要求恢复范围内失败待办时，用公开 `pending.excluded` 和 `show` 核对精确申请、投递、原错误、意见及提交尝试。保持正在运行的批次；下一次初始轮或合法 ready 接续启动时，按本次授权逐个提供 `--recover-request-id <申请ID>`，可重复指定，将这些失败申请与正常队列一起纳入。接续沿用原流程、申请筛选及批次大小，按当前授权追加精确恢复申请。授权失败单与正常单统一按OA接受时间从早到晚排序，历史待办自然先于当天新单；不用失败单独插队，也不把它们排到正常队列清空之后。接续沿用精确恢复清单，同一次投递在这条链内最多恢复一次，恢复后再次失败不循环重试。未授权失败继续排除。

恢复仍重新采集并完整审核，保留旧错误、材料、读取进度和已有识别；它们用于定位和核对，不代替本轮审核完成。仅恢复一个精确申请时也可继续使用 `--request-id <申请ID> --retry-failed YES`。存在未知或未结束提交时只回查；已验证成功或已不在待办中的投递不重试。不通过改库、原轮重领或全局重试恢复。

## 结束与反馈

无待办也按批次规则验收 owner 退出。区分队列耗尽、对话轮换、已有运行跳过和异常阻断。

待办数量使用本轮公开 `pending` 快照，保留原始待办数、选择范围内数量、范围外数量和逐项排除原因。关闭后的 `execution.remaining_count` 为快照原始待办扣除本轮已验证提交，`selected_remaining_count` 为其中仍在本轮选择范围的数量；它们不是关闭时重新拉取的实时队列。`batch.remaining=0` 只说明本批没有排队或在途，不能替代这两个待办数。历史失败及已审核未提交的投递虽未领取，仍是未处理待办，不计本轮新增失败。

本轮没有领取且真实待办仍在时，`execution.status=no_eligible`，采用其首行并说明排除数量及具体原因、下一步和证据，不写“无待审”或“剩余0”，不归档该聊天。本轮状态、剩余数量和仍隔离单据照常如实报告。旧轮没有待办快照时数量未确定，不能从空批次推断真实队列为空。只有快照原始待办为0时才报告无待审；实际提交成功时报告本轮成功数及剩余范围，范围外待办不扩大审批授权。

最终回复和 inbox 首行采用关闭后 `status --view batch` 的 `execution.headline`，同时核对 owner 已退出。`execution.status=blocked/failed/partial_failure` 必须逐行说明原因、已处理事实和下一步；未知提交单列，不把未处理数当失败数。`continued` 按关闭原因说明合法轮换、主动交接或来源暂缓的接续证据。`stopped` 说明用户停止。业务待核不计技术失败。历史 `legacy_unverified` 只表示没有新执行快照，继续核对原回执及聊天证据，不重复通知为新故障。

`status --view batch` 的 `alerts` 表示当前事实，不以命令退出码或聊天结束状态代替验收：

| 告警 | 接管方式 |
| --- | --- |
| `owner_unresponsive` | 执行者忙碌或探测结果不明。间隔 30 秒复查同一轮，核对原 owner 进程和工具会话，核实各阶段是否正常推进 |
| `owner_unreachable` / `owner_mismatch` | 间隔 30 秒复查同一轮并核对原对话、进程及身份；按进度与失联核对处理，身份仍不明时保留现场 |
| `submission_unresolved` / `submission_unverified` | 停止补位和其他写入，有未知或未结束尝试时仅用公开 `postcheck` 核对，已有状态但缺少可核实回执时报告人工核对项。正常活动 Writer 的提交只阻止提前收尾，保留原客户端等待最终结果，不单独误报未知提交 |
| `run_blocked` / `run_closed_with_inflight` | 记录旧轮验收，以 `hourly_dispatch` 判断本轮可执行动作 |
| `technical_failures` | 报告数量和具体错误的证据路径，其余任务按原授权继续 |
| `continuation_pending` | 保存接续事实，下次小时触发用 `start --hourly --continue-from <前轮ID>` 消费，不创建额外对话 |

首次发现阻断或已核实的审核停滞，在当前对话说明原因、实际轮次或 Agent、最后事件及需要的处理；同轮同原因只报告一次，新事实再更新。通知偏好沿用自动任务的既有配置，不新增独立收件箱投递、后台监控或飞书消息。

每次小时检查的私有结果都附 `isolated_failures.items`，包括仍正常运行而跳过、本轮未领单、阻断和启动成功。逐单列 OA 流程编号（`request_id`）、流程、失败阶段、具体原因、证据链接和处理建议。提交失败用公开 show 的精确提交尝试核对回执。缺少证据文件时引用本次状态回执并注明缺口。有实际失败记录时间时报告该时间，否则标明最近尝试所属轮次的启动时间。分别报告 `new_count` 和仍隔离总数，沿用旧轮时本小时新增数按实际变化核实。待办范围按 `pending_snapshot_at` 标注，快照未刷新时注明最近核对时间。未知提交单列，历史隔离单不会重复计为新失败，也无需新增单独通知。隔离清单保留已耗尽自动恢复次数及已有提交尝试的失败单，重试资格单独按 `recovery_candidates` 核对。

意见、数据库和回执保持私有；自动任务记忆不累积业务材料、历史单号或旧队列，只保留原因代码及证据引用。

### 历史聊天保留与变化汇报

业务关闭后仅用公开聊天工具处理历史，范围为本自动任务、固定项目和 local 主机。分页读取历史，核对候选聊天的最终执行事实、对应公开批次回执和执行进程退出。保留当前聊天和仍有运行任务、待用户处理事项或退出状态不明的聊天。

- 成功轮次沿用 `execution.archive_eligible` 和原验收规则。没有执行快照的旧轮次沿用原验收方式，证据不足则保留。
- 本次实际发生失败、部分失败、阻断或异常提前停止的定时任务聊天，按触发时间保留最近 3 轮。正常跳过、正常接续和仅转述历史隔离单的聊天不占异常名额。用户已归档的聊天保持归档。
- 更早的异常轮次在确认聊天和该轮执行均已结束、失败或阻断事实及证据引用已保存后归档。该分支按异常事实核验，无需将旧轮改判为成功。归档只改变聊天可见性，意见、材料、提交记录、回查回执和隔离清单继续保留。

将已核聊天的 ID、分类原因、run_id 和证据引用记入固定 runtime 的 `history-retention.json`。按已核对的 active 与 archived 历史生成归档输入，结构为 `{"complete":true,"rounds":[...]}`。每轮提供 `thread_id`、带时区的定时触发时间 `triggered_at`，以及布尔值 `abnormal`、`archived`、`finished`、`evidence_saved`、`needs_user`。其中 `finished` 表示对话与其执行已核实结束，`needs_user` 表示仍在本对话等待处理。仅在分页和分类都核对完整后设置 `complete=true`。

运行 `bash .codex/python.sh -m apps.oa approvals anomaly-archive-plan --history-file <输入路径> --current-thread-id <当前聊天ID>`。计划只读。仅对 `archive_thread_ids` 中重新核对仍符合条件的目标逐个调用 `set_thread_archived`，并回查已归档。保留 `retained_thread_ids` 与 `protected_thread_ids`。

首次接手或历史状态变化时分页建立同主机 active、archived 清单并保存检查点。后续只核对新增、状态变化和拟归档目标，未变化的旧聊天不重复读取正文；缺少可用检查点时再完整定位。每次归档前仍核对目标、保留名单和当前聊天位置。用户在桌面菜单归档的结果优先于原保留名单。确认菜单归档后，将该目标连同原分类、证据和授权记入 `history-retention.json` 的 `manual_archived`，从 `retained` 移出并保留其归档状态。已归档目标不自动恢复；来源不明时保留现场并仅报告新异常，只有用户另行明确要求恢复指定聊天时才执行。工具拒绝或分页不完整时保留原状态并报告未验证；不写 Codex 状态数据库，不删除聊天或运行证据。归档入口与操作者身份分开记录；菜单来源不证明具体操作者。

历史异常仅在首次发现、分类/原因/数量变化、恢复归档状态或需要新的人工处理时汇报；历史聊天分类同一事实未变时保持原证据。每轮隔离单清单按上节报告，历史失败不计入本轮失败数，涉及失败的条目前加 ❌。不更改自动任务的系统通知策略、周期、模型或启停状态。

归档与通知验收使用真实历史样本。分别核对正常归档、最近 3 轮异常保留、更早且已结束的异常归档、当前聊天保留和手动归档保持。确认只有历史隔离单或正常跳过的轮次不占异常名额，同一历史事实按原规则汇报。无样本的分支标明未验证。证据只保存 ID、分类、核验时间、分页结果及运行证据引用。自动任务 memory 仅记录最新检查点和未验分支，历史完整证据保留在 runtime。
