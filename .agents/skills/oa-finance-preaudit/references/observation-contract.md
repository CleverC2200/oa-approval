# 证据阅读规则

## 两层关系

每条可用证据必须回答两个问题：

1. 为什么该资源属于当前审批单据或具体费用明细？
2. 资源中的哪一处内容支持当前审核项？

第一层关系不成立时，资源不得参与判断；第一层成立但第二层不成立时，只能证明“附件已读取”，不能证明审核项符合。

## 可接受的关系

- OA 或商旅来源返回的稳定资源 ID，并明确绑定当前 requestId；
- OA 明细行直接记录的附件 ID；
- 附件内容同时匹配同一明细的至少两个关键字段，例如金额与日期、路线与乘车人；
- 发票云、官方主数据或表单结构化字段返回的稳定业务关系。

仅有文件名、上传顺序、相似金额、相似日期或模型觉得“像”均不成立。

TPM 终端形象制作费的 `material.tpm_price_reference` 是本地导入并随材料冻结的参考报价。先确认清单属于当前明细，再匹配参考物料；参考表本身不证明当前单据的支出、数量或附件完整。行号和来源哈希用于回查，不把参考表当成 OA 附件；价格适用性按[制作单价规则](flows/tpm-small-marketing-fee.md#制作单价核对归入第一项)核对。

## 付款事实与费用对应关系

六类财务分别核对以下事实，付款事实已核实不等于费用对应关系已闭合：

1. 本笔付款事实：截图能确认的实际支付金额、最终状态及可信退款；
2. 费用对应关系：本笔付款及退款属于哪些当前费用，是否覆盖各组成部分，以及实际交易收款对象与相应发票或费用的可信关系。

付款、退款和发票分别读取成功，只证明各自已覆盖的事实，不证明未显示的费用组成或拆分共享关系。付款扣除退款后的净额与申报或发票合计相等，也不能补足上述关系；不得凭文件名、顺序、单独相同金额或为凑合计反推共享范围。附件字段未解析或页面未显示费用组成时，先检查其他可信字段或附件；仍无法补足时保留具体对应缺口，不把已确认付款或退款改写成未支付，也不把未核实的费用计入已确认核销金额。

OA 报销收款员工、截图付款人和实际交易收款对象按各自角色核对。员工与销售方不同名或付款人姓名未显示，本身不证明实际交易关系有问题。截图实际显示第三方收款对象、但现有交易内容、表单或票据不能可信绑定对应费用或销售方时，仍保留该真实关系缺口；支付成功及金额可读不能代替这项关系核验。按当前科目确定这项关系是否为必需核验，混合单不把某条明细的截图要求扩大到其他科目。

## OA 发票关联与附件内容

上传的发票附件及其内容只能证明票面已提供或已读取，不能证明 OA 已关联。发票号码、附件名称、金额相同以及可读购买方或销售方也不能代替 OA 关联字段或来源明确的可信关联记录。

业务招待、通用费用和 TPM 的发票关联项须按整单核对。全部关联字段未解析、为空且无其它可信 OA 关联记录时，不得使用 `✅`；仅字段未解析时签字意见写“发票关联待核。”，必要时列出受影响明细，解析状态与查询经过留在核对记录中，不能声称申请人未关联。来源已明确关联为空时，模型可依流程规则说明未建立关联。可信关联覆盖拆分明细时不要求每行重复挂票，仍核对错关联、跨单据、多支付对象和重复票据；不能因一行有票就补猜不相关费用的关系。

材料中的 `material.invoice_evidence` 保留逐票的 OA `data_id`、关联字段 `source_field_paths` 和对应票号。发票云已读取的票种、日期、价税合计及买卖方是权威资料，优先用于其实际覆盖的审核事项；字段 `not_provided` 表示该来源未提供，不表示申请人未提供票据。铁路电子客票销售方为空时保持未知，不猜销售方，也不因此丢弃可读票种和金额。

`invoice_evidence.invoices[*].files` 保存同一云发票返回的文件 ID、类型及可用大小。`record_present` 只证明文件记录存在。可信原件经[来源核验](../../../../docs/agents/oa-api.md#关联发票原件读取)、实际下载和全页准备后，记录 `original_source` 的云记录/文件及 OA 文档/主文件身份，并绑定 `resource_id`、原件 `source_content_sha256` 和 `page_count`。文件 `body_read_status=content_read` 表示正文已进入准备材料，审核者仍须读取对应页面或文本后才能形成业务判断。逐票状态仅在全部文件正文已准备时为 `content_read`，部分准备为 `partial_read`，没有正文准备为 `not_read`。未映射文件继续未读；普通上传副本不自动算作云原件。不能仅因附件栏没有重复上传而认定缺票；权威资料和已读取内容仍未覆盖的审核事项，才说明具体读取缺口。照片、付款材料、制作清单等其他附件义务保持各流程规则。读取或原件准备失败按[执行接口](execution-contract.md#采集与提交)保留技术失败，不能转成申请人未提供；明确返回的票号与 OA 关联冲突时不交付为可信事实。

旧冻结材料可能没有 `invoice_evidence`，按原材料读取并披露覆盖限制；不改写历史材料或自动重审。

## 记录方式

Codex 的工作笔记至少保留：

- 来源资源 ID 或表单字段路径；
- 页码、图片区域、表格行或文本锚点；
- 直接看到的原值；
- 它支持的审核项；
- 关系不清时的具体缺口。

表单及权威事实保留在本次工作上下文和已有冻结材料中，附件原值与核对记录通过[执行接口](execution-contract.md#附件观察)保存。材料归属、逐页记录和完整核对不能因公开意见简短而省略；不新增旁路审计文件、证据数据库或持久化表。

## 事实优先级

1. 表单结构化字段和官方权威来源；
2. 可确定性解析并定位的附件内容；
3. 模型对原始页面的视觉读取，区分 Codex 直接观察与 DeepSeek API 识别结果；
4. 无法确认的候选内容，标记为未知。

不得从里程照片的拍摄时间推断费用日期，不得从酒店名猜行政区，不得从报销金额反推付款金额或行程。

## 表单字段读取状态

新采集的 `declared_fields` 保留字段路径、值，以及 `value_source`（`display` 显示值、`raw` 原始业务值、`none` 无可用值）和 `read_status`。`present` 只表示字段已读取，不代表申报内容已经核验符合；`empty` 表示来源字段为空；`unresolved` 表示存在未解析的引用或显示占位提示，不得写成“未填写”。先检查同一事实是否已由其他可信字段或附件确认；例如收款人员 ID 未解析，但同一收款记录的收款人员名称已读取时，应使用名称。只有审核所需事实仍无法确认时，才对受影响审核项使用 `⚠️`，指出具体缺口。

公司、部门等选择字段的内部 ID 不得作为名称比较；客户编码保留前导零。名称原值保留在证据中。仅当当前流程规则明确允许时，才按其范围处理名称排版差异；否则仅去除 HTML 展示格式，不做名称归一化。不得改字、展开简称或做模糊匹配。客户编码已读取但 SAP 主数据未接入时，应写“客户编码已填写，尚未完成主数据核验”，不得写成未填写或核验通过。

旧冻结材料可能没有上述两个新增字段，仍按原版本读取；仅凭旧材料的空 `value` 不能断言申请人未填写，应披露该字段尚未核验。字段来源和解析细节保留在审核材料中，公开签字意见只呈现业务结论和具体待核验事项。

## 页面覆盖

财务附件默认经[DeepSeek 附件识别工具](../../../../docs/agents/attachment-recognition.md)读取，子 Agent 只接收文本回答及逐页来源。自定义问题只覆盖其实际所问内容，识别完成不等于审核完成；原资源归属、固定审核项及高影响原值复读要求保持。识别失败保留技术失败，不向子会话传大图重试。

先在当前任务上下文建立页面覆盖表，再开始看图。逐页按以下顺序分类：

1. `prepared.structured_contents` 的页码和文本已经包含当前审核所需全部原值时，标记“结构化内容已足够”，不进入视觉队列；
2. `prepared.images[*].content_sha256` 与已观察页面相同时，标记“页级精确重复”，复用观察并分别映射全部资源归属；
3. 其余页面按 `owner_detail_id`、`resource_id`、页码和当前审核项直接观察。

页级重复复用须核对 `resource_id`、页面 `content_sha256` 与冻结文件实际字节，记录被复用的代表页并分别映射全部资源、页码及明细。任一哈希缺失、冲突、字节不匹配或代表页未完成读取时，分别覆盖对应的 `prepared.images`。没有可信的审核项专属页面关系时，差旅所有非重复页仍分别适用于八个审核项，不得按文件名、页序、金额、日期或关键词继续裁剪。页面适用范围是覆盖要求，不是业务缺口；使用 `⚠️` 时还须说明该审核项实际缺失的事实或关系，不能仅因没有专属页面关系把八项统一标为待核实。

同一单据由当前审核调用完整读取，不在单据内部建立角色、消息交接或第二套页面队列。涉及版面对应、印章、手写、照片或结构化文字未覆盖区域时仍须读取页面。`source_content_sha256` 只能说明源文件字节相同，不能代替页级覆盖。

## 全页覆盖门禁

形成预审意见前，逐项核对 `prepared.images`：每个页面路径必须对应以下一种记录：

1. 当前 Codex 的直接观察；
2. 同一页面的确定性文本已足以回答当前审核项，并记录跳过视觉读取的原因；
3. 与已观察页面的 `content_sha256` 完全一致，并记录被复用观察的页面标识；
4. 当前问题的 DeepSeek API 文本回答已覆盖该页当前审核所需内容，保留原页引用、问题及识别结果来源，明确这是模型识别。

覆盖记录必须逐页映射回全部 `prepared.images`，包括结构化内容已足够、页级精确重复和进入视觉队列的页面。六类财务流程发现页面缺失、资源身份冲突、归属不可信、PDF 页数与渲染数量不一致或无法解释的未覆盖页面时，不采用对应资源，并把受影响审核项写成 `⚠️` 交财务判断；不得把未执行观察写成“未发现问题”。包装流程缺少可观察页面时按技术失败停止。

金额、主体、日期、里程等高影响事实无法稳定读取时保持 `⚠️` 并写明缺口，不通过投票或语义猜测补齐。
