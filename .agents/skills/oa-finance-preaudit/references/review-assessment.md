# 提交前审核结果

审核 Agent 在最终交付中增加独立的审核结果 JSON 文件，主 Agent 核对后通过 `submit --review-file <绝对路径>` 提交；真实写入必需，海外也沿用此绑定检查。该文件记录已实际执行的核验，不由模板或脚本代填完成结论：

```json
{
  "task_id": 123,
  "material_sha256": "本次公开show中的task.material_sha256",
  "status": "business_pending",
  "reason": "具体已核事项和仍未知的原值，不把未知填零",
  "rule_basis": "当前冻结流程允许保留该未知并交后续判断的具体规则",
  "evidence_files": ["本次material_file绝对路径", "本次原始识别和复读报告绝对路径"]
}
```

`status=complete` 表示全部适用审核已完成且无遗留待核；`business_pending` 表示已完成全部适用处理，按具体流程允许保留业务未知，两者可按授权提交。`incomplete`、`technical_failure` 表示审核未完成，不允许提交完成意见；通过 `fail --task-id ... --reason ... --review-file ...` 保存绑定的失败证据并登记，无需编写意见。采集阶段未形成冻结材料的异常仍由 collect 的诊断入口记录。

证据文件位于本次 `material_file` 的版本目录内，包含本次适用原始识别、复读及观察文件；身份、材料版本、文件归属和存在性由入口核对。程序在预测或外部写入前持久化审核结果及证据摘要。业务待核、审核未完成、读取失败及没有结构化结果的历史材料均保留；提交成功不清除这些保留事实。

入口发现失败识别、未完成读取或冻结材料变化时自行保存 `review-errors` 诊断及实际的 `technical_failure` / `incomplete` 事实，返回 `diagnostics_file`；不能通过下一次省略报告解除同轮、同材料版本的未完成保护。识别仍运行时先等原工具，完整审核后再首次提交；已经交回未完成结果的单据按公开 `fail` 收尾，已有服务端证据时无需重写审核结果文件。后续重试仍按既有精确授权重新采集、完整审核，不自动恢复旧意见。

局部文字不清、金额存在业务冲突或关系未知，按流程完成本单处理后继续 FIFO 补位。只有实际读取技术失败、输出截断或已核实的主会话上下文达到60%才适用小时任务提前停止保护；本单业务未知不等于整批无法读取。
